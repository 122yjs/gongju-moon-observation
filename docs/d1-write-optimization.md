# 기존 반 연결을 보존하는 D1 쓰기 최적화

## 분석 결과와 적용 범위

기준은 `c360a75`이다. 제출 잠금의 중복 UPDATE와 매 요청의 전체 만료 자료 청소는 실제 코드에 있었다.
다만 사진 전달표는 이미 내용이 같은 경우 UPSERT의 UPDATE를 생략하고 있었다.
따라서 목록을 새로고침할 때마다 사진 수만큼 행이 바뀐다는 설명은 정확하지 않다.

Cloudflare의 무료 D1 일일 읽기·쓰기 한도와 초과 시 쿼리 실패는 공식 문서에서 확인했다.
SQL 변경 명령 수와 실제 과금되는 `rows_written`은 구분해야 한다. 인덱스 관리도 쓰기에 포함된다.

| 항목 | 적용 내용 |
| --- | --- |
| 제출 잠금 | INSERT에 이미 담긴 복구용 버전을 다시 UPDATE하지 않는다. 정상 제출 변경 명령은 대략 8회→7회다. |
| 사진 전달표 | 30분 유효기간을 유지한다. 유효한 동일 정보는 변경하지 않고, 만료됐지만 아직 남아 있는 행은 삭제·재삽입 대신 한 번 갱신한다. |
| 만료 자료 정리 | 요청에서 전체 DELETE를 제거한다. Worker 예약 작업이 30분마다 세 임시 테이블에서 각각 최대 500건씩 정리한다. |
| 만료된 제출 ID | 청소가 지연되어도 한 SQL 문장으로 만료된 영수증만 교체한다. 실제로 행을 바꾼 요청 하나만 예약 소유자가 된다. |
| 다른 반 보호 | 같은 관찰 ID가 들어오더라도 다른 반이 소유한 사진 전달표를 덮어쓰지 않는다. |

사진 전달표를 영구화하면 Sheets에서 직접 바꾼 상태나 실패한 공개 상태 변경이 오래 남을 수 있다.
반대로 목록에서 전달표 준비를 없애면 만료된 사진 12개에 대해 Sheets 단건 조회가 추가로 필요해질 수 있다.
따라서 이번에는 목록의 일괄 준비와 유효기간을 유지한다. **갤러리의 모든 상황에서 쓰기가 0회가 되는 변경은 아니다.**
유효한 동일 전달표의 쓰기 0회는 기존 동작을 보존한 것이며, 청소가 이미 삭제한 전달표는 필요할 때 다시 만든다.

## 기존 데이터 호환성

- 테이블·열·외래 키를 바꾸거나 새 마이그레이션을 요구하지 않는다.
- 교사 계정·Google 인증 토큰·학급 ID·초대 링크·Drive 폴더 ID·Sheets ID를 변경하지 않는다.
- 사진·관찰 본문·피드백은 기존 교사 Google Drive/Sheets에 그대로 둔다.
- 행 색인과 하트 구조, 제출 횟수 제한, 시트 잠금의 불확실한 저장 보호를 유지한다.
- 최근 열 밀림 수정인 append의 A:A 탐색 및 A:S 저장 위치 검사를 유지한다.
- 정기 청소는 연결정보·하트·색인·시트 잠금을 삭제하지 않는다. 유효한 임시자료도 삭제하지 않는다.
- 오래된 반의 기존 사진 URL과 만료된 전달표는 원래의 반별 Sheets/Drive 확인 경로로 처리한다.

유효기간과 물리 삭제 시점은 다르다. 정리 실패나 건수 제한으로 만료 행이 남아도 유효한 정보로 사용하지 않는다.
개인정보 안내에 이 차이와 30분 간격 순차 삭제를 반영했다.

## 검증

- 기존 모든 SQL 마이그레이션을 적용한 메모리 SQLite에서 실제 쿼리를 실행했다.
- 완료 영수증 보존, 같은 반과 다른 반의 동시 예약, 만료 경계, 청소 지연 시 요청 ID 재사용을 검사했다.
- 브라우저 10분 3회·학급 1시간 100회 제한과 다른 반 분리를 검사했다.
- 사진 전달표 갱신·권한 분리·공개 상태 변경과 만료 후 원본 재확인을 검사했다.
- 청소 전후 반 연결·토큰·초대 링크·색인·불확실한 잠금·하트를 필드 전체로 비교했다.
- 500건 제한, 후속 정리, 외래 키 무결성과 예약 작업의 오류 전달을 검사했다.
- 빌드 산출물에 예약 작업 함수와 30분 Cron 설정이 포함되고 기존 D1 바인딩 ID가 유지되는지 확인했다.
- 전체 회귀 테스트 227개, 빌드, 변경 파일 ESLint와 `git diff --check`를 통과했다.
- 전체 ESLint는 오류 0개이며 기존 복구 도구에 경고 3개가 있다. `npm test`의 빌드 래퍼는 이 Mac의 GNU `timeout` 부재로 시작하지 못해, 정적 CSS 생성 후 동일한 `vinext build`를 Python의 180초 제한으로 실행하고 전체 테스트를 별도로 실행했다.

이 검증은 합성 자료와 로컬 빌드 기준이다. 운영 데이터 변경이나 운영 배포를 수행하지 않았다.
전체 TypeScript 검사는 기존 12개 오류로 통과하지 않지만, 행 번호를 제외한 진단 내용은 변경 전후 같다.
Miniflare의 로컬 D1 바인딩을 통한 추가 검증은 런타임 준비 단계가 끝나지 않아 중단했고 해당 프로세스는 종료했다.
따라서 실제 D1의 과금 행 수를 측정한 결과로 해석하면 안 된다.

## 배포와 되돌리기

운영 적용에는 기존 배포 절차로 코드와 `wrangler.jsonc`의 Cron Trigger를 함께 반영해야 한다.
추가 마이그레이션이나 기존 반의 재연결은 필요 없다. 배포 후 예약 작업의 성공 및 만료 자료 감소를 확인한다.
작업은 테이블별 500건 제한이 있으므로 밀린 자료가 많으면 여러 차례 실행이 필요하다.
되돌릴 때는 이전 코드와 Cron 설정을 함께 복원한다. 기존 SQL 구조는 유지되므로 데이터 이관을 되돌릴 필요는 없다.
